# 邻里交换平台后台管理项目设计文档

## 1. 项目概述

### 1.1 项目名称
邻里交换平台后台管理系统

### 1.2 项目定位
本项目用于支撑“邻里交换平台”的后台管理与部分业务服务能力，提供管理员登录、用户管理、商品审核、交易管理、公告管理、消息管理、评论管理、统计分析以及个性化推荐等功能。

当前代码仓库同时包含两部分内容：

- 管理端前端：基于 Vue 3 + Vite + Element Plus 的后台管理界面；
- 业务服务后端：基于 Express + MySQL 的轻量级 API 服务，核心实现集中在 `server.js`。

### 1.3 设计目标

- 为后台运营人员提供统一的管理入口；
- 为移动端或小程序端业务提供商品、交易、消息、评论等接口；
- 通过较低实现成本快速完成业务闭环；
- 支撑基础统计分析与个性化推荐；
- 在单体实现基础上，为后续模块拆分预留设计依据。

### 2.4 当前部署特征

- 前端开发服务默认运行在 Vite 端口；
- 后端服务固定监听 `3001` 端口；
- 前端通过 `src/utils/request.js` 动态拼接 `http://当前主机:3001` 访问后端接口；
- 后端与前端位于同一代码仓库，但运行时为两个独立进程。

## 3. 系统总体架构

### 3.1 架构说明

项目采用“前后端分离 + 单体后端文件”的实现方式：

1. 浏览器访问后台管理前端；
2. 前端通过 Axios 调用 `server.js` 暴露的 HTTP 接口；
3. Express 接收请求，完成参数校验、鉴权、业务处理；
4. 后端通过 MySQL 连接池执行 SQL；
5. 统一返回 JSON 结果给前端或业务端。

### 3.2 逻辑架构

#### 表现层

- 后台管理页面
- 登录页
- 看板页
- 用户、商品、交易、消息、公告、评论、管理员等管理页面

#### 接口层

- Express 路由
- CORS 处理
- JSON 请求体解析
- JWT 鉴权中间件

#### 业务层

- 用户认证与资料管理
- 管理员认证与权限入口
- 商品发布、编辑、删除、审核
- 收藏、评论、消息、聊天
- 交易申请与处理
- 统计分析与推荐

#### 数据访问层

- 基于 `mysql2/promise` 的连接池
- 直接执行原生 SQL
- 少量事务控制

#### 数据层

- MySQL 业务表

### 3.3 架构图

```text
+------------------+       HTTP/JSON       +------------------------+       SQL       +------------------+
| Vue3 管理端页面  |  ------------------>  | Express 单体服务       |  ------------>  | MySQL 数据库     |
| Vite + Element   |  <------------------  | server.js             |  <------------  | 业务表集合       |
+------------------+                       | 路由/鉴权/业务/SQL     |                 +------------------+
                                           +------------------------+
```

## 4. 代码结构设计

### 4.1 仓库结构

```text
neighbor_exchange_platform_background_manage/
├─ src/                       前端管理系统
│  ├─ api/                    接口封装
│  ├─ views/                  页面模块
│  ├─ router/                 路由配置
│  ├─ stores/                 状态管理
│  └─ utils/request.js        Axios 封装
├─ server.js                  后端服务入口与全部业务实现
├─ package.json               当前主要维护前端依赖
└─ docs/项目设计文档.md       本设计文档
```

### 4.2 `server.js` 职责划分

`server.js` 当前承担了以下职责：

- 应用启动与端口监听；
- 数据库连接池初始化；
- JWT 鉴权中间件定义；
- 全量路由注册；
- 业务逻辑实现；
- SQL 编写与数据持久化；
- 事务处理；
- 统一返回 JSON 响应。

这种设计开发速度快，但耦合度较高，后续扩展与测试成本也会同步上升。

## 5. 核心模块设计

### 5.1 认证与安全模块

#### 用户认证

- 接口：`GET /login`
- 能力：账号密码登录、密码哈希校验、签发用户 JWT
- 返回：用户信息与 token

#### 管理员认证

- 接口：`POST /admin/login`
- 能力：管理员登录、状态校验、签发管理员 JWT
- 返回：管理员信息与 token

#### 鉴权机制

- 中间件：`authRequired`
- 从 `Authorization` 请求头提取 Bearer Token
- 通过 `jsonwebtoken.verify` 校验 token
- 推荐接口与行为上报接口已接入鉴权

#### 密码存储

- 使用 `bcryptjs` 进行密码哈希；
- 用户与管理员密码均不以明文存储。

- 商品总量、待审核、上架、下架
- 交易总量、今日交易、成功率
- 收藏数、消息数
- 指定时间范围趋势

### 5.11 个性化推荐模块

主要能力：

- 用户行为上报：`POST /behavior/report`
- 推荐商品获取：`GET /goods/recommend`

设计逻辑：

1. 记录用户行为到 `user_behavior`；
2. 优先提取最近点击过的分类偏好；
3. 如果没有点击行为，则退化为最近行为分类；
4. 若仍无偏好，则按热门商品兜底；
5. 推荐结果排除本人商品与已收藏商品；
6. 支持 `keyword` 和 `cate_id` 组合筛选。

该推荐方案属于轻量级规则推荐，适合当前阶段快速上线。

## 6. 数据库设计

### 6.1 主要实体

根据 `server.js` 使用情况及当前数据模型，可识别出以下核心实体：

- 用户：`user_base`
- 管理员：`admin_base`
- 商品：`goods_info`
- 商品分类：`goods_category`
- 商品审核：`goods_audit`
- 商品收藏：`goods_collect`
- 商品评论：`goods_comment`
- 交易记录：`goods_trade`
- 用户地址：`user_address`
- 系统公告：`system_notice`
- 用户消息：`user_message`
- 管理员消息：`admin_message`
- 聊天记录：`chat_record`
- 用户行为：`user_behavior`

### 6.2 核心关系

- 一个用户可发布多个商品；
- 一个商品属于一个分类；
- 一个商品可被多个用户收藏；
- 一个商品可产生多条评论与回复；
- 一个商品可关联多条交易申请；
- 一个用户可维护多个地址，其中一个为默认地址；
- 用户与用户之间可产生聊天记录；
- 用户行为与商品、分类形成推荐输入；
- 管理员负责商品审核与平台治理。

### 6.3 关键字段建议

#### 用户表 `user_base`

- 主键：`user_id`
- 核心字段：`user_account`、`user_pwd`、`user_nickname`、`user_status`
- 扩展字段：头像、简介、经纬度、创建更新时间

#### 商品表 `goods_info`

- 主键：`goods_id`
- 外键：`user_id`、`cate_id`
- 核心字段：名称、描述、图片、成色、类型、价格、交换诉求、库存、状态、浏览量、经纬度

#### 交易表 `goods_trade`

- 主键：`trade_id`
- 外键：`from_user_id`、`to_user_id`、`goods_id`
- 核心字段：交易类型、交换类型、地址、申请价格、申请说明、状态、处理时间

## 8. 核心业务流程设计

### 8.1 用户登录流程

1. 前端提交账号密码；
2. 后端查询 `user_base`；
3. 通过 `bcrypt.compare` 校验密码；
4. 校验用户状态；
5. 生成 JWT；
6. 返回用户信息和 token。

### 8.2 商品发布与审核流程

1. 用户提交商品信息；
2. 后端写入 `goods_info`；
3. 同时写入 `goods_audit` 审核记录；
4. 商品状态初始为待审核；
5. 管理员在后台查看待审核列表；
6. 管理员审核通过后商品上架；
7. 审核拒绝则记录驳回原因。

### 8.3 交易申请与处理流程

1. 申请人提交购买或交换请求；
2. 后端校验商品、物主和交易类型；
3. 写入 `goods_trade`；
4. 处理人审核交易申请；
5. 交易成功时更新当前申请状态；
6. 关闭同商品其他待处理申请；
7. 更新商品状态为已成交或其他业务状态；
8. 发送系统消息通知相关用户。

### 8.4 推荐流程

1. 客户端上报浏览、点击、搜索、收藏等行为；
2. 服务端将行为写入 `user_behavior`；
3. 推荐接口根据最近行为提取分类偏好；
4. 过滤本人商品与已收藏商品；
5. 优先返回偏好分类商品；
6. 不足部分使用热门商品补齐。

## 9. 非功能设计

### 9.1 安全性

已具备：

- 密码哈希存储
- JWT 鉴权
- 基础参数校验
- 部分敏感接口权限限制

仍需完善：

- JWT 密钥需迁移到环境变量；
- 数据库账号密码需迁移到环境变量；
- 管理员接口缺少统一鉴权与角色校验；
- 需补充限流、防暴力破解和审计日志；
- 建议为写操作增加 CSRF/来源控制策略。

### 9.2 可维护性

当前实现优点：

- 单文件开发快；
- 业务逻辑集中，便于快速定位；
- 适合课程项目或早期原型。

当前局限：

- 路由、服务、SQL 高度耦合；
- 文件体量大，阅读与协作成本高；
- 单元测试不易落地；
- 错误处理、鉴权、日志未形成统一中间层；
- 后续新增功能容易继续放大单文件复杂度。

### 9.3 性能

当前具备：

- 使用数据库连接池；
- 统计查询与推荐查询具备基础过滤能力；
- 部分列表接口支持筛选。

优化建议：

- 为高频查询字段建立索引；
- 统一分页，避免全量列表查询；
- 为统计类接口增加缓存；
- 推荐与统计可拆分异步计算；
- 地理位置查询可引入空间索引或距离优化策略。

## 10. 当前实现风险与改进建议

### 10.1 主要风险

- `server.js` 过于庞大，单点复杂度高；
- 前端 `package.json` 未体现 `express`、`mysql2` 等后端依赖，部署时需单独核对；
- 数据库配置和 JWT 密钥硬编码在源码中；
- 仅少数接口接入 `authRequired`，大部分管理接口仍可直接调用；
- 接口风格存在 `GET/POST/DELETE` 混用现象，REST 语义不够统一；
- 事务覆盖面有限，部分跨表操作存在一致性风险；
- 缺少系统化日志、异常追踪和自动化测试。

### 10.2 重构建议

建议按以下结构逐步拆分：

```text
server/
├─ app.js
├─ config/
│  ├─ db.js
│  └─ env.js
├─ middlewares/
│  ├─ auth.js
│  ├─ error-handler.js
│  └─ validate.js
├─ routes/
│  ├─ user.routes.js
│  ├─ goods.routes.js
│  ├─ trade.routes.js
│  ├─ admin.routes.js
│  └─ ...
├─ services/
│  ├─ user.service.js
│  ├─ goods.service.js
│  ├─ trade.service.js
│  └─ recommend.service.js
├─ repositories/
│  └─ 各模块 SQL 访问封装
└─ utils/
   └─ response.js
```

分阶段实施建议：

1. 先抽离配置、数据库、鉴权中间件；
2. 再按业务拆分路由与服务；
3. 对交易、审核等关键流程补事务和测试；
4. 引入环境变量与日志组件；
5. 最后补充分页、统一响应格式与权限系统。

## 11. 结论

该项目已经形成完整的邻里交换平台后台业务闭环，覆盖了用户、商品、交易、审核、消息、评论、统计与推荐等核心能力，适合作为中小型项目原型或课程实践成果。

从设计角度看，当前系统属于“前后端分离 + 单体后端 + 原生 SQL”的快速实现方案，能够满足早期交付需求，但在安全性、模块化、可测试性与部署规范方面仍有较大优化空间。后续若继续演进，建议优先完成后端分层重构、权限收敛、配置外置与关键流程稳态治理。
